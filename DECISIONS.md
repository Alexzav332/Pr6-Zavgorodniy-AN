# DECISIONS.md

## Вариант

Номер варианта: 12 (порядковый номер в группе).

Часть А: добавлен маршрут `EXPRESS` в enum `ApprovalRoute`. Если `urgent == true` И
`amount < 50000` И `risk == LOW` → `EXPRESS`. Приоритет выше R4 (FAST_TRACK): правило
стоит сразу перед R4 и после R1–R3. Порог 50000 вынесен в константу `EXPRESS_LIMIT`.

Часть Б: `addExpressEligibility(long, boolean, RiskLevel, boolean) → boolean` – возвращает
`true`, если заявка подходит для экспресс-маршрута: `urgent == true`, `amount < 50000`,
`risk == LOW`, `containsPersonalData == false`. Иначе `false`.

## Решение 1

Формулировка: метод `route` разбит на проверку контрактов (`checkArguments`) и по одному
private-методу на правило (`requiresSecurityReview`, `requiresDirectorReview`,
`requiresFinanceReview`, `requiresFastTrack`). Тело `route` – последовательность из пяти
коротких `if` в порядке приоритета R1, R2, R3, EXPRESS, R4 и `return STANDARD`.

Альтернатива: записать все условия напрямую внутри `route` одним блоком `if / else if`.

Обоснование: порядок правил виден по одному взгляду на метод, каждое условие читается
и тестируется отдельно, метод получается короче 15 строк. Порог R3 берётся только из
константы `FINANCE_LIMIT`, поэтому смена значения не требует правки логики.

## Решение 2

Формулировка: EXPRESS проверяется после R1–R3 и непосредственно перед R4, а `route`
использует для него тот же публичный метод `addExpressEligibility` из части Б.
Некорректные строки в `sample.csv` и интерактивном режиме не пропускаются молча:
в data-driven режиме такая строка даёт `FAIL data/N: некорректная строка файла: ...`,
в интерактивном – сообщение «Ошибка: ...».

Альтернатива: поставить EXPRESS выше R1 или продублировать условие внутри `route`;
пропускать некорректные строки файла.

Обоснование: персональные данные должны иметь высший приоритет (R1 важнее любой
срочности), а риск HIGH и сумма ≥ 500000 по условию EXPRESS уже исключены, поэтому
правило безопасно стоит сразу над R4. Одно условие в одном методе исключает расхождение
между `route` и методом части Б. Явный FAIL при ошибочной строке не скрывает опечатку в тесте.

## Ответы на контрольные вопросы

### Вопрос 1

Наиболее вероятная ошибка входных данных – параметры, которые не прошли разбор: не
передан уровень риска (`null`) или сумма стала отрицательной. От этого защищает проверка
контракта в методе `checkArguments` класса `ApprovalRouter`, которая вызывается первой
строкой `route`: при `amount < 0` выбрасывается `IllegalArgumentException("Ошибка: amount
must be >= 0, got N")`, при `risk == null` – «Ошибка: risk is null». Эти ошибки
наиболее вероятны, потому что риск и сумма приходят из внешнего источника (файл,
консоль, вызывающий код), где значение легко пропустить или перепутать знак. Без проверки
`null` дал бы тихо неверный маршрут, а не понятную ошибку. Разбор строк (формат, регистр
LOW/MEDIUM/HIGH) вынесен в `SelfCheck`.

### Вопрос 2

Ключевое бизнес-правило – строгий приоритет проверок R1 > R2 > R3 > EXPRESS > R4 > R5,
оно реализовано в методе `route` класса `ApprovalRouter`. Именно порядок `if`
разрешает все пересечения правил: персональные данные важнее HIGH, HIGH важнее суммы,
сумма важнее срочности. Я разместил его в одном месте, потому что `route` – единственная
точка бизнес-логики маршрутизации: метод не имеет состояния и ввода-вывода, его легко
тестировать из `SelfCheck` и переиспользовать. Каждое отдельное условие вынесено
в private-метод, поэтому `route` читается как список правил, а порог R3 хранится в
`FINANCE_LIMIT`, а не в виде числа в условии. Новое правило варианта 12 (EXPRESS) встроено в тот же ряд проверок, не нарушая приоритетов.

### Вопрос 3

Ромб «R2: риск HIGH?» на Activity-диаграмме соответствует строке
`if (requiresDirectorReview(risk)) { return ApprovalRoute.DIRECTOR_REVIEW; }` в методе
`route`. Ветка «да: DIRECTOR_REVIEW» – это `return`, который ведёт к блоку «Вернуть
маршрут согласования»; ветка «нет» – переход к следующей строке, то есть к ромбу R3.
Само условие `risk == RiskLevel.HIGH` находится в private-методе `requiresDirectorReview`.
Новый ромб «EXPRESS» между R3 и R4 соответствует строке с `addExpressEligibility` в
`route`. Порядок ромбов сверху вниз совпадает с порядком строк `if` в коде, а цикла на
диаграмме нет, потому что и в коде нет ни одного цикла – проверки линейные. Для ввода `10000;true;LOW;false` путь: start → R1 (нет) → R2 (нет) → R3 (нет) → EXPRESS (да) → вернуть маршрут → end.

### Вопрос 4

Изменение порога FINANCE_LIMIT с 500000 на 250000 должно затронуть один класс –
`ApprovalRouter`, и в нём одну строку: значение константы `FINANCE_LIMIT`. Логика
методов `requiresFinanceReview` и `requiresFastTrack` не меняется, потому что оба
сравнивают сумму с константой, а не с числом 500000. Остальные классы (`ApprovalRoute`,
`RiskLevel`, `SelfCheck` как код) тоже не трогаются. Изменение локализовано потому, что
порог не размазан по коду, а имеет имя и одно место объявления. Обновить придётся только
ожидаемые значения в тестовых данных, где суммы лежат между новым и старым порогом, –
это изменение данных, а не программы. Именно такую правку я смогу внести на защите за пару минут и сразу проверить полным прогоном `SelfCheck`.

## Фрагмент кода для анализа

В фрагменте `if (urgent) return FAST_TRACK; if (containsPersonalData) return
SECURITY_REVIEW;` нарушен приоритет правил: срочность (R4, низкий приоритет) проверяется
раньше персональных данных (R1, высший). Для заявки `10000;true;LOW;true` код вернёт
FAST_TRACK, хотя по таблице пересечений нужен SECURITY_REVIEW, то есть заявка с
персональными данными обходит контроль безопасности. Правильный порядок: R1 (personal),
затем R2 (HIGH), R3 (сумма), R4 (urgent) и в конце R5 (STANDARD); первое сработавшее
правило возвращает результат, остальные не проверяются.
